VIP Notes: Core Software Quality & V&V Concepts
QUALITY ASSURANCE & TESTING FOUNDATIONS (KEY PRINCIPLES)
✦
SQA vs QC vs Testing: SQA is process-oriented & preventive across the full SDLC; QC is product-oriented inspection verifying deliverables against standards; Testing executes the software to detect runtime faults.
✦
Defect Chain: Human Error (mental mistake) → Fault / Bug (flaw encoded in source/spec) → Failure (dynamic deviation from required behavior during execution). A fault may remain dormant!
✦
IEEE 1012 V&V: Verification: "Are we building the product right?" (Conformance to specifications, static reviews); Validation: "Are we building the right product?" (Fulfilling customer/user true operational needs).
✦
Quality Models: McCall categorizes factors into Product Operation, Product Revision (Maintainability, Flexibility, Testability), and Product Transition. ISO/IEC 25010 modernizes this for web/cloud services (Security, Compatibility, Performance Efficiency).
Part I: Multiple Choice Questions (5 Marks)
Q1 [Midterm 2026]

Which of the following best distinguishes Software Quality Assurance (SQA) from Software Quality Control (QC)?

a) SQA focuses on identifying defects in the final executable product, whereas QC focuses on establishing coding standards.
b) SQA is product-oriented and detects bugs at the testing stage, whereas QC is process-oriented and prevents defects from the start.
c) SQA is process-oriented, spanning the entire lifecycle to prevent defects, whereas QC is product-oriented, evaluating deliverables against standards before release.
d) SQA and QC are synonymous terms used interchangeably to describe execution-based testing activities.
✓ Correct Answer: C

Rationale: SQA is proactive and process-driven, focusing on managerial and engineering processes across the entire SDLC to prevent defects. In contrast, QC is product-driven, using inspections, reviews, and tests to evaluate final deliverables and ensure they conform to requirements before release.

Q2 [Midterm 2026]

According to McCall’s Quality Model, which of the following quality factors belong exclusively to the Product Revision category?

a) Correctness, Reliability, Efficiency
b) Portability, Reusability, Interoperability
c) Maintainability, Flexibility, Testability
d) Usability, Integrity, Safety
✓ Correct Answer: C

Rationale: McCall's model divides factors into three perspectives: (1) Product Operation (Correctness, Reliability, Efficiency, Integrity, Usability), (2) Product Revision (Maintainability, Flexibility, Testability), and (3) Product Transition (Portability, Reusability, Interoperability).

Q3 [Midterm 2026]

In the context of the software error-fault-failure chain, which statement is scientifically most accurate?

a) Every software error immediately causes a software fault, and every fault results in a system failure.
b) A software error is a human action resulting in an incorrect result, a fault is the adjudged cause of an error in the code, and a failure occurs only when that fault is executed and activated under specific conditions.
c) A failure is a human mistake made during requirements gathering, while a fault is a dynamic runtime exception.
d) Errors and faults can only be detected through dynamic execution testing, whereas failures are identified through static code reviews.
✓ Correct Answer: B

Rationale: According to IEEE/ISO terminology, an Error is a human cognitive mistake. A Fault (bug/defect) is the physical manifestation of that error in software artifacts. A Failure is an observable dynamic deviation from expected behavior, which occurs only if the fault is activated during program execution.

Q4 [Midterm 2026]

When evaluating software deliverables, a team conducts a requirements walkthrough and checks design documents for completeness and consistency without executing code. This activity is best classified as:

a) Dynamic validation testing
b) Verification
c) Quality Control bug tracking
d) Performance stress testing
✓ Correct Answer: B

Rationale: Static analysis activities such as peer reviews, inspections, and walkthroughs of intermediate lifecycle deliverables (requirements, design docs) evaluate conformance to standards without code execution, which constitutes static Verification.

Q5 [Midterm 2026]

Why would an enterprise development team choose the ISO/IEC 25010 quality model over McCall's classic model for modern cloud-native microservices architecture?

a) ISO/IEC 25010 is obsolete and only used for legacy desktop applications.
b) McCall's model includes explicit sub-characteristics for Security, Compatibility, and distributed Performance Efficiency required by modern SaaS systems.
c) ISO/IEC 25010 provides modern characteristics and sub-characteristics (such as Security, Compatibility, and Performance Efficiency) specifically suited for distributed and web-based environments.
d) ISO/IEC 25010 eliminates the need for any formal software testing or quality assurance plans.
✓ Correct Answer: C

Rationale: ISO/IEC 25010 replaces ISO 9126 and expands McCall's model by establishing explicit, refined characteristics critical for distributed and cloud architectures—notably Security (Confidentiality, Integrity, Non-repudiation), Compatibility (Coexistence, Interoperability), and Performance Efficiency (Time behavior, Resource utilization).

Part II: True or False Questions (5 Marks)
TF 1 [Midterm 2026]

Software Quality Assurance (SQA) is primarily a post-hoc inspection gate applied right before software deployment.

A) True
B) False
✓ Correct Answer: B (False)

Rationale: SQA is an ongoing, preventive umbrella activity integrated throughout all SDLC stages, not merely an end-of-pipe or post-hoc inspection gate before deployment (which describes late Quality Control/Release Acceptance).

TF 2 [Midterm 2026]

In static testing, developers and testers evaluate work products such as requirements, user stories, and source code without executing the component or system.

A) True
B) False
✓ Correct Answer: A (True)

Rationale: By definition, static testing relies on manual examinations (reviews, inspections, walkthroughs) and tool-based static analysis of code and documentation without dynamic CPU execution.

TF 3 [Midterm 2026]

According to IEEE 1012, verification answers the question "Are we building the right product?", while validation answers "Are we building the product right?".

A) True
B) False
✓ Correct Answer: B (False)

Rationale: The definitions are reversed. Verification evaluates whether deliverables conform to specified requirements ("Are we building the product right?"), whereas Validation evaluates whether the system satisfies its intended operational use and user needs ("Are we building the right product?").

TF 4 [Midterm 2026]

A software fault may remain completely dormant and undetected in the code for a long time until a specific event or input activates it.

A) True
B) False
✓ Correct Answer: A (True)

Rationale: A fault is static code defect. Unless test cases or operational inputs execute that exact branch or condition under activating environmental states, the fault remains dormant and produces no observable system failure.

TF 5 [Midterm 2026]

ISO 9001 is a widely used standard that provides guidelines for establishing a Quality Management System (QMS) to ensure consistent quality in products and services.

A) True
B) False
✓ Correct Answer: A (True)

Rationale: ISO 9001 sets out the criteria for an organization-wide Quality Management System (QMS) based on process orientation, continuous improvement, and customer satisfaction.

Part III: Essay Questions & Model Answers (5 Marks)
E1

Compare and contrast Software Quality Assurance (SQA), Quality Control (QC), and Software Testing in terms of: (1) Primary focus (Process vs. Product), (2) Timing across the SDLC, and (3) Primary responsibility (Who performs them).

Comparison Dimension Software Quality Assurance (SQA) Quality Control (QC) Software Testing
1. Primary Focus Process-oriented: Defect prevention by defining, tailoring, auditing, and improving lifecycle processes and standards. Product-oriented: Defect detection and verification of deliverables against established requirements before release. Execution-oriented: Sub-activity of QC focused on running code with specific test cases to observe runtime failures.
2. Timing across SDLC Entire SDLC: Continuous from project inception, requirements engineering, through development, deployment, and maintenance. Milestones / Pre-release: Applied at specific review gates and completion of intermediate/final deliverables. Build & Integration Phase: Dynamic testing happens once executable modules/builds exist (alongside early test design).
3. Primary Responsibility SQA Team & Process Owners: Independent SQA engineers, process auditors, and project leadership. QC Reviewers & Inspection Teams: Peer reviewers, technical leads, and inspection panels. Test Engineers & Developers: Dedicated QA testers, automation engineers, and developers (unit/integration tests).
E2

Examine the lifecycle of a software defect by explaining the progression from Error to Fault to Failure.

  • 1. Error (Mistake / Human Action): A psychological or cognitive human mistake made by a software engineer, analyst, or architect during requirements drafting, design modeling, or code implementation (e.g., misinterpreting an off-by-one loop condition or arithmetic boundary).
  • 2. Fault (Defect / Bug): The physical manifestation and internal consequence of an error encoded into a software artifact (source code, documentation, or configuration file). A fault is passive and can lie dormant indefinitely without causing issues if the affected code path is not triggered.
  • 3. Failure (Dynamic Deviation): The dynamic, observable departure of the operational software system from its required or expected behavior. A failure occurs if and only if the dormant fault is executed, activated by specific input parameters and system states, and produces an erroneous external state.
  • Summary Progression: Human Error → Injects Fault into Artifact → [Execution & Trigger] → Observable System Failure.
E3

Clearly differentiate between Testing and Debugging in terms of their objectives and who performs them upon encountering an anomaly.

Attribute Software Testing Debugging
Primary Objective To discover faults and anomalies by purposefully provoking failures through systematic execution against expected results, assessing overall product quality and conformance. To investigate, localize the exact root cause of the known failure (locating the dormant fault in the code), design a fix, and repair/re-factor the code to remove the bug.
Who Performs It? Performed primarily by Software Test Engineers / QA Specialists (independent verification role) as well as developers during unit testing. Performed exclusively by Software Developers / Programmers who have code access and architectural domain expertise.
Workflow Position Precedes debugging: Testing identifies and logs the failure incident into a defect tracking system. Triggered by testing: Developers take the bug report, reproduce the symptom, step through code, patch it, and submit for re-testing.
E4

Discuss the concept of the "Two Faces of Software Quality": Quality of Design and Quality of Conformance. Define both terms and list the core activities associated with each face.

  • 1. Quality of Design:
    • Definition: Reflects how well the requirements, system architecture, specifications, and grade of the product meet customer expectations, domain constraints, and user experience objectives.
    • Core Activities: Requirements elicitation & analysis, market research, usability and UX modeling, architectural design trade-off analysis, formal specification reviews, and establishing robust design patterns.
  • 2. Quality of Conformance:
    • Definition: The degree to which the implemented code, executable software, and end product faithfully adhere to the agreed-upon design specifications, standards, and engineering guidelines.
    • Core Activities: Code reviews, static code analysis, unit/integration/system testing, compliance audits, continuous integration pipelines, and defect management.
  • Key Principle: Excellent conformance cannot rescue a fundamentally flawed design, and a brilliant design is rendered useless if the implementation lacks conformance. Both faces are essential for software success.
E5

Define Verification and Validation (V&V) in software engineering: (a) Contrast their objectives, timing, and whether they rely primarily on static or dynamic analysis techniques. (b) Discuss the economic impact of delaying validation activities until late in the development cycle versus integrating them continuously.

  • Part (a): Contrast of Verification & Validation
    ParameterVerificationValidation
    Governing Question"Are we building the product right?""Are we building the right product?"
    Core ObjectiveEnsure deliverables strictly conform to the specifications and inputs established in preceding lifecycle phases.Ensure the integrated software fulfills the actual customer requirements, operational workflows, and intended use.
    TechniquesPrimarily Static Analysis: Inspections, code reviews, walkthroughs, and static analysis tools.Primarily Dynamic Testing: System testing, acceptance testing (UAT), alpha/beta releases, and operational testing.
    TimingContinuous across every SDLC phase from requirements to implementation.Traditionally evaluated upon executable build completion, but increasingly integrated continuously.
  • Part (b): Economic Impact (Cost of Quality & Boehm's Law)
    • The Cost of Change Escalation: According to Boehm's cost-of-change curve, the cost of remediating a defect escalates exponentially (up to 50× to 100×) when an architectural or requirement misconception is detected late during final system validation or post-deployment compared to early detection.
    • Delaying Validation Risk: Deferring validation until final delivery introduces severe risks of "building the wrong system perfectly" (high conformance to flawed requirements), resulting in catastrophic redesigns, blown budgets, schedule slippages, and potential project abandonment.
    • Continuous Validation Benefit: Integrating early, continuous validation (via rapid prototyping, agile user story acceptance, and continuous deployment feedback) catches misalignments immediately, lowering the cost of rework, shortening time-to-market, and maximizing ROI.
